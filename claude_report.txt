### Correctness & Robustness

**Blockers:**

- B-1: Off-by-one string length in `src/math/picocalc_math.c:21`.
  The code reads:
    return mp_obj_new_str("SuperCalc.OG-hybrid-proof-0.2", 28);
  "SuperCalc.OG-hybrid-proof-0.2" is 29 bytes (confirmed by character count).
  `mp_obj_new_str(data, len)` in MicroPython uses the explicit length, not
  null-termination. On real hardware, `picocalc_math.version()` will return
  "SuperCalc.OG-hybrid-proof-0." — the final character '2' will be missing.
  The host test harness does NOT catch this because it exercises only the Python
  fallback path (which returns "pure-python-fallback-0.2"). This will be
  discovered the moment the module is first tested on device.
  FIX REQUIRED: Change `28` to `29`, or replace with
    return mp_obj_new_str("SuperCalc.OG-hybrid-proof-0.2",
                          strlen("SuperCalc.OG-hybrid-proof-0.2"));
  to make all future string returns robust against edits.

**Major Issues:**

- M-1: `complete-phase` subcommand missing from ralph.sh.
  PGR.md (Tool Usage section) lists `complete-phase`, `set-phase`,
  `generate-handoff`, `record-hardware-verification`, and `list-handoffs` as
  "useful subcommands" of ralph.sh. PHASES.md Phase 0 success criterion explicitly
  states "Automation script runs cleanly (`status`, `complete-phase` demo)".
  None of these subcommands beyond `status` and `help` are implemented in ralph.sh.
  Calling `./tools/ralph.sh complete-phase` fails with a misleading error.
  FIX REQUIRED: Either (a) implement a `complete-phase` subcommand that generates a
  timestamped handoff, updates LOOP_STATE.json, and prints the review prompt — OR
  (b) update PHASES.md and PGR.md to correctly describe what the tool actually does
  and reformulate the success criterion accordingly. Option (a) is preferred because
  it aligns the tool with the documented implementer workflow.

- M-2: False-positive clearance detection in `ralph.sh` (phase_cleared function).
  The function uses:
    grep -qiE "CLEARED TO CONTINUE|PHASE COMPLETE|CLEARED TO ADVANCE|APPROVED"
  The bare term `APPROVED` matches text that can appear in a non-clearance review.
  For example, a review with "Overall Assessment: APPROVED WITH MINORS" in the
  header but "NEEDS WORK - DO NOT ADVANCE" as the final verdict would incorrectly
  match and advance the phase. This undermines the quality gate.
  FIX REQUIRED: Remove `APPROVED` from the grep pattern. The formal clearance
  signals are already fully specified by `CLEARED TO CONTINUE` and
  `PHASE COMPLETE - CLEARED TO ADVANCE`. The bare `APPROVED` adds no value and
  introduces false-positive risk.

### Risks & Technical Debt

1. String length fragility (B-1): The off-by-one pattern in the one C function that
   returns a string literal is a risk class if it propagates to Phase 1 where many
   more C functions will be added. Fixing with `strlen()` at the source establishes
   the correct pattern for all future additions.

2. False-positive loop advancement (M-2): An incorrectly advancing phase means the
   quality gate fails silently. The loop's value depends on this being correct.
   Must be fixed before the loop runs at scale.

3. Device validation gap: All C code correctness claims are unverified on real
   hardware. Phase 1 must establish a device smoke test workflow before new C
   numeric functions are declared "working".

4. MICROPY_FLOAT_IMPL_DOUBLE unconfirmed: If the base firmware uses single-precision,
   the double-precision baseline silently fails in Phase 1. Low-probability risk
   (LofiFren for RP2350 should have double enabled) but worth explicit confirmation.

5. Build pipeline unexercised: The end-to-end build (clone base + Docker + UF2) has
   not been run. The instructions are correct and well-documented, but until the user
   executes them at least once, there may be base-port-specific surprises. This is
   the expected human bring-up step.
