### Correctness & Robustness

**Blockers**:

B-1: C iterator API is incorrect for MicroPython — will not compile against real MicroPython headers.

In src/math/picocalc_math.c lines 128-131:

    mp_obj_iter_t it;
    mp_obj_get_iter(tokens_in, &it);
    mp_obj_t item;
    while ((item = mp_iternext(&it)) != MP_OBJ_STOP_ITERATION) {

Multiple errors here:
1. mp_obj_iter_t does not exist in the MicroPython public C API. The correct type is mp_obj_iter_buf_t (defined in py/objiter.h).
2. mp_obj_get_iter(o, iter_buf) returns an mp_obj_t — this return value is discarded. The returned iterator object is what must be passed to mp_iternext.
3. mp_iternext takes an mp_obj_t argument, not a pointer-to-struct. Calling mp_iternext(&it) passes a pointer to a local stack variable where an mp_obj_t is expected — this is a type mismatch that will either fail to compile or produce undefined behavior at runtime.

The correct pattern from MicroPython source:

    mp_obj_iter_buf_t iter_buf;
    mp_obj_t iter = mp_obj_get_iter(tokens_in, &iter_buf);
    mp_obj_t item;
    while ((item = mp_iternext(iter)) != MP_OBJ_STOP_ITERATION) {

Because all testing is done via the Python fallback (HAS_C_MATH=False on host), this defect is invisible until UF2 build time. It must be corrected before the C path can be claimed working.

**Major Issues**:

M-1: Unary minus has higher precedence than power in the infix parser, producing non-standard (wrong) results.

In mp/lang/expr.py lines 141-152:

    def _precedence(op):
        if op in ("neg",):
            return 4          # higher than ^
        if op in ("^", "pow"):
            return 3

With this table, -2^2 parses as (-2)^2 = 4. The universally expected mathematical result is -(2^2) = -4. This is true on all HP calculators (HP-41, HP-48/49/50), in Python (-2**2 == -4), and in every standard mathematical convention. A user typing -2^2 on day one will get the wrong answer with no indication.

The fix: lower "neg" precedence to be below "^" (e.g., return 0.5, or treat it as lower than add/sub), then update the parser to handle unary-minus emission correctly. In the shunting-yard algorithm, unary minus is typically handled by emitting a 0 and a binary minus, or by treating it as a right-associative unary op with lower-than-power precedence.

M-2: Power operator ^ is left-associative instead of right-associative, producing non-standard results for chained exponentials.

In push_op (expr.py line 62):

    while op_stack and op_stack[-1] != "(" and _precedence(op_stack[-1]) >= _precedence(op):

With >=, 2^3^4 parses as (2^3)^4 = 8^4 = 4096. The mathematically standard (and HP-48 standard) result is 2^(3^4) = 2^81 approx 2.4e24. Exponentiation is right-associative in virtually all mathematical contexts and all HP calculators.

The fix: for ^ and pow specifically, the while-loop condition must use strict > (not >=) so that equal-precedence power operators are right-associative:

    _right_assoc = {"^", "pow"}
    while op_stack and op_stack[-1] != "(" and (
        _precedence(op_stack[-1]) > _precedence(op) or
        (_precedence(op_stack[-1]) == _precedence(op) and op not in _right_assoc)
    ):

Both M-1 and M-2 are in the infix parser only (to_rpn). The RPN path is unaffected.

**Minor / Observations**:

m-1: mp_raise_ValueError_varg (picocalc_math.c line 223) — this variadic form may not exist in all MicroPython builds. The standard pattern is mp_raise_msg_varg(&mp_type_ValueError, fmt, ...). Verify against the exact LofiFren/zenodante build's MicroPython version before relying on it.

m-2: Op-name aliases ("add", "sub", "mul", "div", "pow") that are supported by the C rpn_eval and eval_rpn are NOT handled by eval_rpn_str's tokenizer (expr.py line 324). A string like "2 3 add" would parse "add" as a ("var", "add") tuple, which then fails with "undefined variable: add" when eval_rpn processes it. Minor inconsistency in the convenience API.

m-3: eval_rpn() bypasses the C stack machine entirely: it calls individual hybrid leaf functions (add, sin, etc.) from a Python-managed stack. The C rpn_eval is only invoked via eval_infix (after variable resolution). This is architecturally justified (sto/rcl/vars must live in Python), but it means the advertised "C hot path for RPN" is not exercised in the primary RPN entry mode. Document this explicitly in ARCHITECTURE.md or expr.py module docstring, so future phases don't assume eval_rpn is C-accelerated.

m-4: pow() in the C kernel (picocalc_math_pow, line 104-108) does not guard against complex-result inputs. pow(-1, 0.5) returns NaN silently, while sqrt(-1) raises ValueError. The behavior is inconsistent. Acceptable for Phase 1 scope but should be recorded in DECISIONS.md as deliberate.

m-5: test_expr.py has no test case for -2^2 (the unary-minus/power precedence bug) and no test for 2^2^3 (the associativity bug). Without these, the Major defects above went undetected by the test suite.

m-6: LOOP_STATE.json records last_completed_phase: -1, meaning Phase 0 was never formally closed (hardware verification still pending human). This is accurate, but note it for tracking.

### Architecture & Hybrid Design

The C/MicroPython boundary is thin and explicit. picocalc_math.c exposes a flat list of named functions and one rpn_eval entry point that accepts a Python iterable — this is the right shape. MPy owns parsing and variable state; C owns numerics. This is correct and well-documented.

The hybrid.py dispatch pattern (try C import, fallback to pure Python) is clean and the fallback implementations are faithful mirrors of the C semantics. The HAS_C_MATH flag is accessible to callers for informational purposes.

One architectural clarity gap (m-3 above): the primary eval_rpn path does not use the C stack machine. This is acceptable for Phase 1 (vars/sto/rcl justify the Python stack), but document it so that Phase 2 VM design does not assume the wrong entry point for RPN evaluation.

micropython.cmake (5 lines) is minimal and correct for USER_C_MODULES registration.

### HP Programmable Spirit

Phase 1 inc1 correctly lays the foundation:
- dup, drop, swap, over — present in both C kernel and Python layer
- neg/chs — present (HP CHS key equivalent)
- sto/rcl with env dict mutation — correct HP-style variable side effects
- Predefined constants (pi, e, phi) — accessible from both infix and RPN

The precedence and associativity issues (M-1, M-2) are particularly relevant here: HP-48 users expect -2^2 = -4 and 2^3^4 to be right-associative. Getting these wrong on the infix side will immediately feel wrong to the target audience. In pure RPN mode the user controls the stack explicitly so the issues don't apply — but the infix mode must match mathematical convention.

Deferred items (ROLL, DEPTH, locals with ->, named programs, control flow) are correctly out of scope for Phase 1.
